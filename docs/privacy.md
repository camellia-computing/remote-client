# Camellia Remote privacy boundary

Camellia Remote is pre-release software. This document describes the source baseline; it is not a jurisdiction-specific consumer privacy notice and does not announce a hosted service.

The client handles device identifiers, network addresses, authentication material, clipboard content, transferred files, session metadata, optional recordings, and diagnostic logs as required by features the user enables. Remote-session content is exchanged with the selected peer and, when direct connectivity fails, the configured relay. Account, policy, device, and audit requests go only to the management endpoint configured by the operator. The baseline does not compile in a Camellia telemetry, update, rendezvous, relay, or management endpoint.

Connection auditing uses protocol version 3. The host opens one Management-bound `starting` audit session after receiving the peer login request, fixes the authenticated controller identity to enter `active`, then serializes authorization, heartbeat, file, alarm, and terminal events through the Management-issued UUIDv4 capability. A 20-second monotonic heartbeat refreshes the default 90-second database-time lease. The Client uses one ordered 64-item queue, preserves two slots for lifecycle termination, retries lifecycle events with the same event ID for at most the lease window, and never lets an unreachable Management service create unbounded memory growth. The capability is never accepted from the peer and is not persisted as an account secret. File and Alarm evidence is authoritative only after the controller independently binds the same active, unexpired session with its Management device bearer; this binding is independent of the optional end-of-connection note prompt. Pre-session or unbound alarms remain local diagnostics and are not uploaded as authoritative evidence. Controller notes use a fresh event ID for each revision. Both native and Flutter clients reject legacy, malformed, non-UUIDv4, mismatched-acknowledgement, regressing-revision, terminal-state, or expired-lease responses. Management records a normal close as `closed`, an end before authorization as `aborted`, and missing close telemetry as `expired/telemetry_lost`; no client treats the latter as a successful disconnect.

When an operator explicitly enables incoming-recording upload, unfinished recovery metadata is stored next to the local recording in two checksummed sidecar slots. They use mode 0600 on Unix and inherit the recording directory's ACL on Windows. The metadata contains the local path, a hash of the configured Management origin, opaque upload identifiers, committed byte counters, SHA-256 digests, and finalize/abort state; it does not contain the account bearer token. Sidecars are removed after an authenticated finalize or abort acknowledgement. A process restart resumes only a recording already marked ready to finalize and aborts an ambiguous active recorder, so partial content is not represented as a completed server recording. Retryable Management responses (429, 503, and 507) preserve that state and impose a bounded server-provided retry window instead of causing one request per recorded frame; Management remains authoritative for quota and retention.

Credentials and permanent-password material use platform-protected or encrypted local storage where implemented. Logs must not contain passwords, access tokens, private keys, clipboard/file contents, or full device-verification secrets. Operators control their servers, retention, backups, access policy, and any legal notice required for their deployment.

Before distributing a build connected to a hosted service, the distributor must publish an accurate service-specific privacy notice, identify the controller and contact route, document purposes, retention, subprocessors, transfer locations, user rights, and incident handling, and ensure that the compiled configuration matches that notice.

Do not report private data or vulnerabilities in a public issue. Follow [SECURITY.md](../SECURITY.md).
